# Support Agent 四期知识空间冻结方案

> 版本：1.0；冻结日期：2026-09-27；状态：已冻结；对应实施计划已编制、待用户确认，禁止仅据本文直接开始编码。

## 1. 背景与结论

Support Agent 面向单个企业私有化部署。每套部署只服务一个企业，因此四期不引入多租户，也不在所有业务表中增加 `tenant_id`。用户模块继续承担认证、审计、个人会话、工单发起人和个人长期记忆等职责，不能删除或退化为单一共享账号。

当前系统只有“用户私有资源”和“全局共享知识”两个层次：会话、工单和长期记忆按用户归属，托管文档和已发布案例进入同一个全局检索池。该模型无法表达部门、产品线、客户项目或业务领域的知识边界，也可能造成跨领域信息暴露和检索噪声。

四期冻结结论是新增“知识空间”作为企业内部知识共享、隔离和检索的核心边界，形成以下三层模型：

1. 个人层：用户自己的会话、个人长期记忆和工单发起关系。
2. 业务域层：按产品线、业务领域、客户项目或专业团队划分的知识空间。
3. 企业层：所有有效用户均可读取的企业公共知识空间。

## 2. 四期目标

- 在不引入多租户的前提下，为企业内部知识建立明确的共享与隔离边界。
- 让托管文档、工单、已解决案例和聊天会话具有稳定的知识空间归属。
- 让 BM25、向量召回、RRF、Rerank 前候选和 MySQL 来源有效性回查遵守同一空间权限。
- 保留用户级长期记忆，但把它严格限定为个人信息，不承担团队公共知识职责。
- 保持已发布知识和案例的人工审核、版本化、归档、引用与安全网关能力。
- 为后续部门或用户组映射预留稳定边界，但不在四期实现组织架构。

## 3. 四期不在范围

- 多租户、租户管理、租户级数据库或索引隔离。
- 企业部门树、岗位、汇报关系、动态组织规则或复杂 RBAC。
- LDAP、OIDC、企业 SSO 或外部身份供应商的真实接入。
- 自动把聊天内容沉淀为团队长期知识。
- 使用模型自动决定用户权限、自动发布知识或自动扩大知识可见范围。
- 跨知识空间的默认全局检索、自动联邦检索或跨空间知识复制。
- 空间级共享长期记忆、环境画像或配置中心。
- 空间成员协同处理原始工单；四期工单详情权限继续遵守现有“本人或平台管理员”规则。
- 新模块、新中间件、独立向量数据库或每空间一个 Elasticsearch 索引。

## 4. 核心术语

### 4.1 知识空间

知识空间是单个企业内部稳定的业务与知识边界，可对应产品线、业务领域、客户项目或专业团队。知识空间不是租户，也不等同于企业部门。

一个用户可以加入多个知识空间，一个知识空间也可以由多个部门或团队共同使用。用户调岗不应改变历史文档和案例的空间归属。

### 4.2 企业公共空间

系统必须存在一个代码固定为 `GLOBAL` 的企业公共空间：

- `GLOBAL` 在首次迁移时由系统创建。
- 所有有效用户隐式拥有 `GLOBAL` 的读取权限，不为每个用户复制读取成员记录。
- `GLOBAL` 不得删除、停用或修改代码。
- `GLOBAL` 的编辑和管理仍需显式权限；平台管理员保留治理能力。
- 历史无空间数据统一迁移到 `GLOBAL`，以保持升级前后的可见性和检索行为。

### 4.3 受限空间

除 `GLOBAL` 外的空间默认采用显式成员授权。空间可以承载 ERP、支付、网络、客户项目等知识。未获得该空间读取权限的用户不得通过检索、引用、来源详情或其他接口推断其知识内容是否存在。

`visibility=ENTERPRISE` 表示所有有效用户隐式拥有读取权限，但编辑和管理仍需显式成员角色；`visibility=RESTRICTED` 表示读取、编辑和管理均要求成员权限。除系统 `GLOBAL` 外，四期新建空间默认使用 `RESTRICTED`，将空间扩大为 `ENTERPRISE` 必须由平台管理员显式执行并记录审计。

## 5. 冻结领域模型

### 5.1 `knowledge_space`

知识空间至少包含以下稳定语义；精确 SQL 类型、索引和 API DTO 由后续实施计划冻结：

| 字段 | 含义与约束 |
|---|---|
| `spaceId` | 对外稳定 UUID，创建后不可变 |
| `code` | 企业内唯一、稳定、区分大小写的空间代码；`GLOBAL` 为系统保留值 |
| `name` | 用户可见名称 |
| `description` | 空间用途和知识边界说明 |
| `visibility` | `ENTERPRISE` 或 `RESTRICTED`；四期除 `GLOBAL` 外默认 `RESTRICTED` |
| `status` | `ACTIVE` 或 `DISABLED`；停用后禁止新写入和新会话选择 |
| `version` | 乐观锁版本 |
| 审计字段 | 创建、更新主体及 UTC 时间 |

四期不物理删除知识空间。存在历史资源的空间只能停用，不能通过删除破坏审计和引用。

### 5.2 `user_space_membership`

用户与空间为多对多关系，同一用户在同一空间最多一条有效成员关系。空间角色固定为：

| 角色 | 权限语义 |
|---|---|
| `READER` | 选择该空间进行聊天和检索，查看允许公开的知识来源元数据 |
| `EDITOR` | 包含 `READER` 权限，可创建和修改该空间的知识草稿 |
| `MANAGER` | 包含 `EDITOR` 权限，可管理成员，并执行发布、归档等空间治理操作 |

空间角色与平台角色相互独立。平台 `USER` 可以成为某空间的 `MANAGER`，平台 `ADMIN` 保留所有空间的治理和审计能力，但日常业务治理应优先使用空间角色。

四期直接维护用户成员关系，不实现部门或用户组到空间的批量映射。

### 5.3 既有资源归属

以下资源必须新增非空空间归属：

| 资源 | 四期空间语义 |
|---|---|
| 托管文档 | 创建草稿时明确选择空间；发布、归档和索引始终沿用该空间 |
| 工单 | 表示问题所属业务域；仍保留 `ownerUserId` 表示发起人 |
| 已解决案例 | 从来源工单继承空间，正常流程中不得选择不同空间 |
| 会话 | 创建时绑定当前活动空间；用于限定该会话的检索范围和工单归属 |
| Elasticsearch 分块 | 冗余稳定的 `spaceId`，供 BM25 和向量召回在搜索侧先过滤 |

异步任务、运行记录和检索轨迹通过关联资源或运行上下文获得空间，不在四期无依据地复制新的业务所有权。

## 6. 会话与空间选择

- 新会话必须具有一个活动知识空间。
- 用户只能选择自己可读的 `ACTIVE` 空间；`GLOBAL` 始终可选。
- 空间在一次会话代际内保持固定，避免不同业务域的历史、摘要、证据和工单建议混合。
- 用户需要切换空间时，应新建会话，或通过既有重置语义开始新的会话代际；不得在保留旧上下文的情况下原地切换。
- 从聊天建议创建的工单继承会话空间；手工创建工单必须显式选择用户可读空间。
- 四期不使用模型自动改变会话空间。前端可以要求用户选择，服务端必须再次校验。

## 7. 检索与权限不变量

### 7.1 检索范围

一次普通问答只检索：

```text
GLOBAL + 当前会话活动空间
```

当活动空间本身是 `GLOBAL` 时只检索 `GLOBAL`。即使用户同时拥有多个空间权限，也不得默认把所有空间合并召回。跨空间问答属于后续能力，必须另行冻结。

### 7.2 双重权限校验

空间权限必须同时落在以下两个位置：

1. Elasticsearch 的 BM25 和向量查询在召回前按允许的 `spaceId` 过滤。
2. MySQL 来源有效性回查同时校验来源状态、版本和空间是否属于本次允许范围。

只在 Controller、前端或 Elasticsearch 单点过滤均不满足安全要求。检索应用端口必须显式接收不可为空的访问上下文和活动空间，不得继续依赖无主体的 `retrieve(query)` 语义。

任何空间不存在、已停用、成员关系失效、索引字段缺失或权限上下文无法确定的情况都必须失败关闭，不得退化为全局检索。

### 7.3 索引策略

- 继续使用统一的版本化 Elasticsearch 物理索引和业务别名，不按空间创建独立索引。
- 新索引 Mapping 必须把 `spaceId` 定义为 `keyword`，并保持严格动态映射。
- 必须通过新版本索引全量重建、完整性验证和原子别名切换完成升级。
- 旧索引中没有 `spaceId` 的文档不得在空间权限启用后继续提供检索。
- 归档、版本失效和空间权限过滤的先后不能改变最终不可见结论。

## 8. 文档、工单与案例规则

### 8.1 托管文档

- 草稿创建者必须对目标空间具有 `EDITOR` 或 `MANAGER` 权限。
- 发布和归档要求 `MANAGER` 或平台 `ADMIN` 权限。
- 已发布文档不得直接改变空间。确需迁移时，应按“归档旧来源、在目标空间创建并重新审核发布”的可审计流程处理。
- 内容哈希去重至少在同一空间内生效；是否允许相同内容存在于不同空间，由实施计划结合现有唯一约束确定迁移方案，但不得借去重接口泄露其他空间内容。

### 8.2 工单

- `ownerUserId` 与 `spaceId` 含义不同，二者必须同时保留。
- 普通用户四期仍只能查看和修改自己的工单；空间成员资格不会自动授予原始工单详情权限。
- 平台管理员继续可以查看全部工单。
- 空间级支持人员协同、指派和队列属于后续候选能力，不进入四期。

### 8.3 已解决案例

- 案例生成时复制来源工单的 `spaceId`，并在发布前校验二者仍一致。
- 案例发布后只进入其所属空间的检索范围；不得因为发布者是平台管理员而进入全企业范围。
- 案例跨空间发布必须被拒绝。需要进入其他空间时，应创建独立、经过脱敏和人工审核的知识文档。
- 发布审核必须继续防止把工单中的个人信息、凭据或不应跨人员传播的内容沉淀为案例。

## 9. 个人长期记忆与共享知识边界

现有 `user_memory` 继续按用户隔离、默认关闭、候选确认后才注入，并保持用户可更正、撤销和永久删除的治理方式。

允许作为个人长期记忆的内容包括：

- 回答语言、格式、详细程度等个人偏好。
- 个人工作站、个人默认工具等仅代表本人的环境信息。
- 只约束本人的工作习惯或个人约束。

以下内容不得作为个人长期记忆承担企业事实职责：

- 产品或服务的统一版本、架构和部署方式。
- 部门、业务域或项目共同遵守的流程与规则。
- 共享服务器、生产环境、网络拓扑和公共配置。
- 企业制度、客户项目事实或团队排障结论。

上述共享事实应进入对应知识空间的托管文档或已审核案例。四期不新增空间级“长期记忆”表，也不允许模型从个人聊天自动提升为共享知识。

## 10. 历史数据兼容与迁移原则

- 升级时创建系统 `GLOBAL` 空间。
- 所有历史托管文档、工单和已解决案例回填到 `GLOBAL`，保持现有可见性，不根据创建人或正文猜测业务域。
- 历史已发布文档和案例必须重建到包含 `spaceId` 的新索引后，才能启用范围化检索。
- 历史 Redis 会话不根据内容推断空间；实施计划应选择可验证的兼容策略，例如统一绑定 `GLOBAL` 或让旧会话自然过期。
- 数据库迁移只追加，不修改既有 Flyway 文件，不使用级联删除。
- 迁移前后必须能够核对每个已发布来源的空间、版本和分块数量，不允许静默丢失知识。

## 11. 公共契约方向

后续实施计划必须为以下契约变化给出精确 DTO、错误码、兼容窗口和 OpenAPI 示例：

- 知识空间列表与详情。
- 空间创建、修改、停用和成员管理。
- 托管文档、工单和案例响应中的 `spaceId` 与空间摘要。
- 创建文档、手工创建工单和开始会话时的空间选择。
- 检索、聊天和案例发布的空间权限错误。

四期不得仅依靠前端隐藏实现权限。所有访问控制必须由认证上下文进入应用层用例并再次校验，Controller 不能直接决定资源可见性。

## 12. 安全、审计与可观测性

- 空间创建、修改、停用、成员增删和角色变化必须记录安全审计事件。
- 审计记录不得包含知识正文、对话正文、密码、Token 或模型原始响应。
- 检索指标只允许记录低基数结果，例如是否包含 `GLOBAL`、活动空间类型、允许空间数量区间和拒绝原因；不得把 `spaceId`、空间名称或用户 ID作为指标标签。
- 日志可以通过受控关联标识排障，但不得输出用户无权访问的空间名称或知识摘要。
- 禁用用户、撤销成员关系或停用空间后，新请求必须立即按新权限失败；既有 Bearer Token 不能绕过应用层空间校验。
- LLM 输入安全策略和输出安全网关继续覆盖空间知识、个人记忆、会话历史和案例草稿，不因新增空间而放宽。

## 13. 四期验收结果定义

四期实现完成后，至少应达到以下业务结果；具体测试命令和用例数量由实施计划冻结：

- 无权限用户无法通过聊天、搜索、引用、详情或错误信息发现受限空间知识。
- 同一个问题在不同活动空间中只使用 `GLOBAL` 与对应空间的证据，不发生跨空间串扰。
- BM25 和向量检索均执行空间过滤，MySQL 回查可以阻止伪造或过期空间候选。
- 文档、工单、案例和会话均具有可追溯空间归属，案例与来源工单空间一致。
- 历史数据迁移后可见性不意外扩大，已发布知识无静默丢失。
- 个人长期记忆仍仅按用户注入，共享业务事实不通过个人记忆传播。
- 平台管理员与空间角色边界、审计事件、乐观锁和越权测试全部通过。

## 14. 后续分期候选方向

以下仅用于说明四期预留边界，不属于已冻结范围，也不预先分配第五期或其他期次：

- 候选方向：部门或用户组映射、空间支持人员工单队列、受审核的空间共享上下文。
- 候选方向：真实 SSO/目录同步、跨空间联邦检索、知识生命周期和影响分析增强。

上述能力必须在用户确认具体产品期次后形成独立冻结方案，不能从本节直接推导实现。

## 16. 变更控制

修改空间可见性、空间角色、`GLOBAL` 语义、资源空间归属、检索范围、案例继承规则、长期记忆边界、历史迁移策略或四期不在范围前，必须先修订本文并取得用户明确确认。

对应实施计划见 [四期知识空间实施计划](../implementation-plan/12-phase-4-knowledge-space-plan.md)。在用户明确确认计划并下达单个阶段执行指令前，不得修改业务代码、数据库迁移、公共接口或 Elasticsearch Mapping。
