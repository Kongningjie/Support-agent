# Support Agent 二期优化实施计划

> 状态：已冻结，是阶段 6～9 的执行与验收依据；阶段 6～9 已完成。
>
> 版本：1.2；冻结日期：2026-09-09；最后更新：2026-09-19；一期阶段 0～5 已完成，本计划只描述后续质量、性能和稳定性优化。

## 1. 文档目的

本文冻结 Support Agent 二期优化目标、阶段边界、指标口径和验收门禁。D1～D10 已经用户逐项确认；后续实现不得脱离本文自行扩大范围或修改门槛。

## 2. 优化原则与默认边界

- 优先顺序确认为：回答与检索质量 > 稳定性 > 响应速度 > Token 和基础设施成本。质量明显下降时，不得仅凭更低延迟或成本采用候选方案；质量相当时再依次比较稳定性、响应速度和成本。
- 先测量基线，再修改实现；任何优化必须提供优化前后使用同一数据和口径的对比报告。
- 现有 50 条固定中文问题作为锁定回归集，不得为提高分数修改标注或针对单条问题编写特殊规则。
- 参数只允许离线对比、人工确认后修改；不实现线上自动调参或自学习。
- 默认保持 Java 21、Spring Boot 4.1、Maven 六模块单体、AgentScope、DashScope、MySQL、Redis、Elasticsearch 和 Outbox，不引入 RocketMQ。
- 默认不新增前端、多租户、长期记忆、多 Agent、MCP Server或备用模型供应商。
- 新增依赖、中间件、公共 API、数据表、状态或业务流程前必须单独确认。

## 3. 统一指标口径

### 3.1 检索质量指标

| 指标 | 字段含义 | 冻结目标 |
|---|---|---:|
| `Recall@5` | 期望来源是否至少有一个出现在前 5 个结果中 | ≥ 0.90 |
| `MRR@10` | 第一个正确来源在前 10 个结果中的平均倒数排名 | ≥ 0.85 |
| `nDCG@5` | 前 5 个结果同时考虑相关等级和排序位置的质量 | ≥ 0.85 |
| `noHitAccuracy` | 无可靠知识问题被正确判断为无知识的比例 | 1.00 |
| `exactTermRecall` | 错误码、命令、版本、路径等精确词问题的正确召回比例 | 1.00 |

这些质量硬门槛只约束生产默认模式 `HYBRID_RERANK`；另外三种模式用于分析各检索环节的贡献。阶段 6 只负责测量，即使当前值低于门槛也不判定阶段 6 失败，阶段 7 必须达到门槛。若阶段 6 实测基线高于表中数值，后续实际门槛取二者较高值，避免优化后退化。

### 3.2 延迟与可靠性指标

| 指标 | 字段含义 | 冻结目标 |
|---|---|---:|
| `retrievalP95Ms` | 从收到检索请求到得到最终 Top 5 的 P95 耗时 | ≤ 3,000 ms |
| `modelFirstTokenP95Ms` | 服务端调用 Chat 模型到收到首个模型 Token 的 P95 耗时 | ≤ 3,000 ms |
| `safeFirstDeltaP95Ms` | 请求开始到客户端收到首个已通过完整答案校验片段的 P95 耗时 | ≤ 15,000 ms |
| `answerCompleteP95Ms` | 请求开始到发送 `answer.completed` 的 P95 耗时 | ≤ 20,000 ms |
| `requestSuccessRate` | 非用户参数错误请求中成功完成的比例 | ≥ 99% |
| `onlineRegressionPassRate` | 锁定在线样例在同一模型版本下的通过比例 | 100% |

`modelFirstTokenP95Ms` 与 `safeFirstDeltaP95Ms` 必须分别记录：当前安全方案会先完整校验答案再向客户端发送正文，二者不是同一个指标。

上述表格适用于持续 2 RPS 的正常负载。20 个不同会话同时请求的突发场景要求成功率不低于 95%、`answerCompleteP95Ms` 不超过 30,000 ms，且不得发生线程、HTTP 连接、Redis 租约或 SSE 队列泄漏。用户参数错误、同会话预期冲突、客户端主动取消和慢客户端保护测试不计入请求成功率；DashScope 限流或超时、MySQL/Redis/Elasticsearch 故障及程序异常均计入系统失败。

### 3.3 成本指标

- 分别记录 Chat 输入 Token、Chat 输出 Token、Embedding 文本数及字符数、Rerank 候选文档数。
- 报告单次请求平均值、P95 和评测批次总量，不在日志中保存完整 Prompt、知识正文或模型输出。
- 阶段 6 只建立基线；本计划不设置人民币成本硬门槛，模型评测统一执行 D5 的 Token 预算。正式计费方式明确后如需成本目标，必须另行变更冻结方案。

## 4. 评测数据治理

数据固定分成三套，避免在同一批问题上反复调参导致虚假提升：

1. **锁定回归集**：保留现有 50 条问题及 15 条语料，只用于回归和最终验收，不因优化结果修改标注。
2. **优化开发集**：新增 150 条自编中文问题，用于选择分词、分块和排序参数。数据固定分为：30 条直接知识、30 条同义及噪声、30 条精确词、20 条多轮及查询改写、20 条无知识或越界、20 条冲突或歧义。
3. **真实业务集**：上线或试运行后，从脱敏工单构建第二套独立验收集；必须移除姓名、账号、密钥、内网地址和可识别业务数据。

数据引用应改用稳定的 `sourceKey`，不得继续依赖空库中的 MySQL 自增 ID。每个问题必须说明问题分类、期望来源、相关等级、是否应无命中、涉及的精确词、是否依赖多轮上下文及是否存在知识冲突。优化开发集允许用于参数实验，锁定回归集只用于最终回归，不得依据其单条结果编写特判。

## 5. 阶段 6：评测治理与基线测量

### 5.1 目标

建立可重复、可对比、不会被调参污染的质量、延迟、可靠性和成本基线，不改变生产检索参数。

### 5.2 必须交付

- 固化锁定回归集的版本、内容哈希、稳定来源标识和校验规则。
- 建立独立优化开发集，并检查类别分布、重复问题、答案泄漏和标注一致性。
- 在四种检索模式下生成统一质量报告，报告包含 Git 提交、数据集版本、模型名、参数快照和运行时间。
- 增加检索、Embedding、Rerank、模型首 Token、安全首片段和完整请求耗时统计。
- 统计模型用量，不记录敏感正文。
- 执行单用户、5 并发、20 并发基线；持续负载为 2 RPS，短时峰值为 5 RPS。

### 5.3 并发测试方法

容量目标确认为 20 个并发会话、持续 2 RPS、短时峰值 5 RPS。测试分为以下三层，避免把模型额度、第三方限流和本地代码瓶颈混为一谈：

1. **本地容量测试**：通过专用 Maven Profile 启动完整应用和本地基础设施，使用测试范围内的确定性模型适配器，不调用 DashScope。客户端使用 Java 21 `HttpClient` 和虚拟线程发起真实 HTTP/SSE 请求，不新增生产依赖。
2. **真实在线并发抽样**：在明确授权和 Token 上限内使用真实 DashScope，分别执行 1、5、20 个不同会话的同步起跑批次，用于观察第三方模型延迟、限流和连接释放；不得用它替代本地持续负载测试。
3. **竞争与慢客户端测试**：单独验证同一会话并发请求的租约冲突、客户端主动取消、SSE 消费过慢、超时以及资源回收。这类预期拒绝不计为容量测试失败，但结果必须符合既有错误和事件契约。

每个正常并发请求使用不同的 `sessionId` 和 `clientMessageId`，防止会话互斥机制把容量测试误变成冲突测试。使用起跑闩锁使请求在同一时刻开始，并完整消费到 `answer.completed` 或 `error`，记录成功数、错误类型、检索耗时、模型首 Token、安全首片段和完整耗时。

执行序列固定为：单请求预热 5 次；5 并发执行 3 轮；20 并发执行 3 轮；持续 2 RPS 执行 5 分钟；5 RPS 执行 30 秒峰值。持续和峰值测试默认使用确定性模型；真实模型测试的请求数和 Token 总量由阶段 8 预算限制。

### 5.4 验收门禁

- 相同提交、数据、模型和参数重复运行两次，质量指标完全一致；在线延迟报告允许波动但必须保留原始统计摘要。
- 锁定回归集未被修改或用于单条特判。
- 输出阶段 6 实测基线、与冻结门槛的差距和阶段 7～9 的优化重点，不在执行过程中擅自改写冻结门槛。

## 6. 阶段 7：检索质量优化

### 6.1 目标

提高中文自然表达、错误码、命令、配置、路径和冲突知识的召回及排序质量，同时保持无知识判断可靠。

### 6.2 候选优化项

- 对比当前 ICU 分析器与针对中文技术词的最小分析配置；未经数据证明不引入新的大型分词组件。
- 对比目标 600/800/1000 字符、最大 1000/1200/1500 字符及少量重叠的分块组合。
- 对比 BM25/Vector Top K、`RRF(k)`、融合 Top K、Rerank 候选数和最终 Top K。
- 检查标题、精确词、来源类型是否需要有限且可解释的权重。
- 优化同义改写、混合中英文、拼写噪声及精确词保护。
- 校准可靠知识门槛，分别检查误回答和误判无知识，禁止只追求召回率。

### 6.3 实施约束与验收

- 每次实验只改变一组可说明的变量，保存参数矩阵和完整报告。
- 不允许为固定问题增加硬编码特判，不允许自动修改线上参数。
- 冻结参数必须同时满足质量门槛、无显著延迟退化，并在锁定回归集上不退化。

## 7. 阶段 8：模型回答、延迟与成本优化

### 7.1 目标

在不削弱引用、事实边界和完整答案校验的前提下，选择正式 Chat 模型并降低延迟和无效 Token 消耗。

### 7.2 候选优化项

- 使用同一小型回答评测集比较 `qwen3.7-flash-2026-07-15`、`qwen3.8-flash` 和 `qwen3.8-max-0902`。前者是已验证基线，后两者分别作为新一代低延迟候选和高质量上限候选。
- 三个模型使用相同 Prompt、生成参数和 30 条代表性问题：10 条明确知识、5 条精确词、5 条无知识、5 条知识冲突、5 条案例结构化生成。
- 比较维度包括：事实依据、引用正确性、精确值保真、无知识克制、结构遵循、首 Token、完整耗时和 Token 用量。
- 独立评估 Intent、普通 Chat、案例结构化生成；不得因为 Chat 模型选择而合并三个适配接口。
- 压缩重复上下文和 Prompt，但不得删除安全规则、证据编号或输出 Schema。
- 保留“完整答案校验后再发送”和“最多完整重生成一次”的安全策略。
- 每个 Chat 候选独立设置 100,000 Token 硬上限和 80,000 Token 预警线；输入、输出、完整重生成及供应商可能已计费的失败请求均计入。先运行 30 条代表性问题一轮，只对不稳定样例运行第二轮。达到硬上限后立即停止该模型的后续评测，并为单次回答设置最大输出 Token。
- 普通 Chat 和回答评测固定 `temperature=0.0`，关闭思考模式；回答上限为 1,200 Token，意图识别为 256 Token，工单和案例结构化生成为 800 Token。
- 质量评测对象是完整生产链路：第一次完整生成后执行答案校验；校验失败时携带错误原因完整重生成一次；第二次仍失败才视为该生产链路失败。客户端始终不会看到未通过校验的正文。完整链路最终失败或调用异常时，评测器允许额外执行一次独立稳定性复测，两类重试分开统计。

### 7.3 验收门禁

- 正式模型必须通过全部在线回归样例和安全校验。
- 模型选择按硬门禁执行：先检查事实准确、引用正确、无知识克制、精确值保真和结构化输出；未通过质量门禁的候选直接淘汰。质量均通过时依次比较稳定性、响应速度和 Token 消耗，不允许用加权平均分掩盖质量不合格。
- 与阶段 6 基线相比，质量不得下降；若以更高成本换取质量，报告必须明确提升幅度和成本差异，由用户决定。
- 模型名称、版本、超时和 Token 上限必须配置化，密钥仍只通过环境变量注入。

### 7.4 冻结选型结论

- `qwen3.7-flash-2026-07-15` 作为已验证基线，`qwen3.8-flash` 作为新一代低成本候选，`qwen3.8-max-0902` 作为质量上限候选。三者使用同一数据、Prompt、生成参数和硬门禁，因此比较不依赖模型世代或名称假设。
- 最终选择 `qwen3.8-flash`：30 条用例首轮全部通过，无生产重生成和稳定性复测；其他候选在同轮仍存在硬门禁失败。选择依据依次是质量、首轮稳定性、完整回答 P95、Token 和 Flash 偏好，不使用加权总分。
- 压缩 Prompt 未通过全部质量门禁，且未达到输入 Token 至少下降 10% 的采用条件，故正式配置保留 `ORIGINAL`。

## 8. 阶段 9：稳定性与运行准备

### 8.1 目标

消除一期已知运行风险，完成依赖故障、任务积压、恢复和容量验证。本轮不实现认证授权，继续使用一期固定操作者 `dev-operator`；认证、角色和企业身份接入必须另建方案。

### 8.2 候选优化项

- 明确 Chat、Embedding、Rerank、Elasticsearch、Redis、MySQL 的连接和读取超时。
- 仅对安全且幂等的调用执行有限重试和带抖动退避，验证超时、取消和资源释放。
- 增加 Outbox 积压量、最老任务等待时间、重试次数、`DEAD` 数量和处理吞吐指标。
- 评测执行进度继续保存在内存；完成后生成不可变 JSON 报告，记录 `runId`、Git 提交、数据集版本与哈希、模型名、参数快照、起止时间和全部指标。应用重启时未完成运行视为中断，完整报告继续保留；不新增数据库表，不把动态报告提交到 Git。
- 验证 MySQL 备份恢复、Elasticsearch 重建索引、Redis 丢失后的会话降级及案例/文档归档一致性。
- 处理 SpringDoc/Jackson Schema 兼容性警告，但不得盲目升级 Spring Boot 或替换文档技术栈。
- 根据阶段 6 压测证据决定是否调整 Worker 并发、连接池和资源限制；没有积压证据时不引入 RocketMQ。

### 8.3 验收门禁

- 达到已冻结的容量、延迟、成功率和任务恢复目标。
- 关键依赖故障不会被错误解释为“无知识”，不会泄露供应商响应或半成品答案。
- 完成安全检查、恢复演练、完整 Review、单元测试、集成测试、在线测试和阶段记录。

## 9. 暂不纳入本计划的内容

- 前端界面、移动端、复杂工单流程和业务报表。
- 多租户、长期记忆、多 Agent、MCP Server、备用模型供应商。
- RocketMQ、向量数据库替换、微服务拆分、Kubernetes 和独立在线评测平台。
- 未经确认的认证授权、组织架构和角色权限设计。

这些内容不是“不需要”，而是会改变业务或架构边界，必须建立独立方案后再实施。

### 9.1 后续独立会话压缩阶段

本节决策已细化并冻结为 [三期会话记忆优化实施计划](09-phase-3-conversation-memory-plan.md) 的阶段 10；后续实现以三期文档为唯一执行入口。

- 会话压缩抽象为独立应用服务，不与 Chat 适配器或 AgentScope 具体实现绑定；摘要模型固定为 `qwen3.7-flash`。
- 触发条件不固定为 30 条，应根据消息条数和估算 Token 双阈值配置；压缩较早消息，保留最近完整轮次。
- 摘要使用结构化契约，保留用户目标、已确认决策、约束、未解问题和关键实体；关键实体必须回溯源消息校验，不接受摘要模型凭空新增。
- 摘要在正常回答后异步生成；达到硬上限且异步摘要尚未可用时，同步降级生成。Redis 只保存当前会话摘要，TTL 与现有会话统一为 7 天，更新使用版本号/CAS 防止并发覆盖。
- 跨会话长期记忆属于再后续的独立阶段，需另行确认用户身份、授权、数据模型、删除与合规边界，不与本地会话摘要混合实现。

## 11. 冻结与变更控制

- 本文 1.2 版本自 2026-09-19 起生效，D1～D14、阶段边界、指标口径和验收门禁均为冻结内容。
- 阶段 6 的基线数据只能决定后续优化重点，不得自动降低已冻结的质量、延迟或成功率门槛。
