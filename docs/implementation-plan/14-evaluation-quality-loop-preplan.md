# Support Agent 评测体系优化专项预规划

> 状态：批次 1 用户回答反馈已完成；批次 2 人工评测已单独冻结并实施；批次 3 LLM-as-Judge 已冻结并实施，在线校准未验证。本文不是独立编码入口。与五期 Agent 能力扩展预规划并列，正式产品期次和阶段编号待排期时确定。

## 1. 目标与现状

在现有固定中文数据集、检索指标、回答硬规则、安全和空间隔离评测之上，建立“用户反馈—人工复核—评测集回归”的质量改进闭环，并用 LLM-as-Judge 辅助扩大语义质量评测覆盖面。阶段 8 的 30 条回答用例、阶段 17 的 80 条安全用例和阶段 20 的 60 条空间隔离用例继续作为独立基线。真实在线摘要质量、真实模型对抗和非 `GLOBAL` 空间真实问答的未验证状态不因本规划改变。

## 2. 按顺序实施的三个批次

| 顺序 | 批次 | 目标与最小交付 | 验收重点 |
|---:|---|---|---|
| 1 | 用户回答反馈 | 登录用户对本人一次已完成的回答提交“有帮助/无帮助”、预定义原因和可选说明；关联稳定运行标识，支持本人更正及管理员按权限查看聚合结果 | 不能反馈他人会话或未完成回答；重复提交、修改、删除、并发及敏感信息处理可验证；反馈不得自动改写知识或模型参数 |
| 2 | 人工评测 | 从脱敏的失败反馈和固定样本中抽样，按统一量表评价事实正确、引用支持、完整性、可操作性和表达清晰度；记录评审结论与分歧处理 | 至少两人对样本独立评分、分歧复核、评审留痕；经确认的困难样本进入独立开发集，再按冻结流程晋升回归集 |
| 3 | LLM-as-Judge 辅助评测 | 对脱敏回答和允许展示的证据按固定评分契约生成逐维度评分、理由和证据位置；与人工标注对照，输出一致性及误判报告 | 评审模型不得接触越权证据或原始敏感数据；必须评估同源模型偏差、复测稳定性、成本及人工一致性；不得单独决定发布或上线 |

每批次单独形成冻结设计、测试门槛、工作记录和完整 Review；上一批次验收完成后再启动下一批次。批次 3 可以使用批次 2 的人工结论校准，但不得用 Judge 自己的分数替代人工真值。

## 3. 共同边界

- 引用是否合法、精确值是否有证据、权限隔离、安全拦截等继续由现有确定性门禁判定；人工或 Judge 评分不能覆盖硬失败。
- 用户反馈只是质量信号，不等于事实正确；不得由点赞数直接训练模型、自动发布案例或自动调整检索参数。
- 采集遵循最小化原则：不在指标、普通日志或评测报告中保存完整 Prompt、模型输出、工单原文、密钥或个人信息。样本晋升前必须脱敏并人工确认使用范围。
- 评测数据按空间和用户权限隔离。用户只能操作本人反馈；人工评审和管理员查询的权限、保留期与审计需在相应批次冻结。
- 复用现有 Java 21、Spring Boot 4.1、MySQL、Redis、Elasticsearch、DashScope 与前端技术栈；新增模型调用只在明确预算和授权下进行。不因本规划引入新中间件或独立评测平台。

## 4. 每批次实施前需冻结的决策

1. 用户反馈对应的回答标识、可见范围、原因枚举、编辑窗口、保留和删除策略，以及前后端交互——批次 1 已冻结并实现，详见下方链接。
2. 人工评审抽样规则、评分量表、复核角色、脱敏标准、数据集版本与标注变更流程。
3. Judge 的模型、独立适配边界、提示词、评分契约、调用预算、人工一致性门槛和失败处理。
4. 三批次各自的数据库迁移、接口字段、权限、审计、固定测试数据、在线测试授权和量化验收阈值。
