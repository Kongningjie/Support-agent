# 前端工程与 AI Coding 强制规范

## 1. 环境与命令

- 默认开发环境为 Windows 11、PowerShell 7、Node.js 24.x LTS、npm 11.x。
- 所有命令必须使用 PowerShell 语法；不得提供只适用于 Bash 的 `export`、`rm -rf` 等命令。
- 依赖安装统一使用 `npm ci`；只有明确变更依赖时才使用 `npm install <package>` 并提交 `package-lock.json`。
- 不提交 `node_modules/`、`dist/`、Playwright 报告、测试截图、`.env`、Token、密码或本地日志。

## 2. TypeScript 与 Vue

- TypeScript 开启严格模式；禁止使用未说明原因的 `any`、非空断言和宽泛类型转换。
- Vue 组件统一使用 Composition API 与 `<script setup lang="ts">`，Props、Emits 和插槽必须显式声明类型。
- 组件使用 `UpperCamelCase.vue`；组合函数使用 `useXxx.ts`；Store 使用 `xxx.store.ts`；API 文件使用 `xxx.api.ts`；类型文件使用 `xxx.types.ts`。
- 页面只编排交互，不直接拼接 URL、解析 SSE 或访问 `sessionStorage`；这些能力必须由对应 API、组合函数或 Store 封装。
- 导出的类型、组合函数、Store Action 和复杂私有辅助函数必须有简体中文 JSDoc，说明职责、参数、返回值、错误和关键约束。
- 不建立无边界的 `utils.ts`。只有具备稳定单一职责且至少有两个真实调用方时才抽取共享能力。

## 3. 状态和数据流

- Pinia 只保存认证会话、当前聊天等跨页面状态；普通列表、筛选和表单状态保留在页面或组合函数中。
- 服务端数据是最终事实。写操作成功后使用响应对象更新本地状态，不能凭前端假设自行推进版本或状态。
- 所有写请求必须防重复提交；需要幂等键时，在一次用户动作开始时生成并在结果不确定的重试中复用。
- 乐观锁冲突不得静默覆盖。页面保留未提交输入，提示用户刷新最新数据后再次确认。
- 时间在 API 层保持 UTC ISO-8601 字符串，格式化只发生在展示层。

## 4. HTTP、SSE 与错误

- 普通 REST 统一经过 Axios 实例，不允许页面各自创建客户端或复制拦截逻辑。
- SSE 统一经过单一 `fetch` 流客户端；Parser 必须处理 Chunk 切分、多行 `data`、空行分帧、UTF-8 边界和异常终止。
- Abort 不作为系统错误弹窗；真正网络失败、服务端 `error` 事件和 HTTP 错误必须区分。
- 前端错误对象至少保留 HTTP 状态、业务 `code`、公开 `message`、`traceId` 和是否可重试；不得把 Axios/Fetch 原始对象直接显示给用户。
- `401` 清理认证状态；`403` 不伪装成资源不存在；`409` 按状态或版本冲突处理；`422` 显示安全/内容校验提示；`503` 明确依赖暂不可用。

## 5. 安全

- DashScope API Key 永远只存在后端环境，前端不得提供配置入口。
- Bearer Token 只允许进入 Authorization 请求头、Pinia 内存和 `sessionStorage`；禁止打印、拼入 URL、复制到错误报告或写入快照。
- 用户、模型、知识和工单文本一律按不可信内容处理。默认使用文本节点；模型 Markdown 必须使用冻结的 markdown-it `html=false` 与 DOMPurify 链路，并限制链接协议。
- 外部链接使用 `rel="noopener noreferrer"`；文件上传限制必须与后端类型和大小规则一致。
- 角色菜单、隐藏按钮和路由守卫不替代后端授权，不能依赖客户端提供操作者身份。
- 所有 `.env*` 中只有 `.env.example` 可以提交，且只能包含非敏感占位配置。

## 6. UI 与可访问性

- 使用统一设计令牌管理颜色、间距、圆角、阴影和字体，不在页面散布无意义魔法值。
- Element Plus 负责通用控件；业务组件只封装真实重复语义，不机械包装每个按钮和输入框。
- 表单字段必须有可见标签、校验信息和必填说明；弹窗打开后焦点合理，关闭后焦点返回触发元素。
- 加载、空数据、失败、无权限、已过期和冲突必须有不同反馈，不以一个“暂无数据”覆盖全部情况。
- 状态不能只用颜色表达；交互元素支持键盘操作并具有可访问名称。

## 7. 测试规范

- 测试文件使用 `*.spec.ts` 或 `*.spec.tsx`；页面端到端测试使用 `*.e2e.spec.ts`。
- 单元测试不得依赖真实后端、Docker、网络或真实密钥；通过明确的 HTTP/SSE Fixture 验证客户端行为。
- 必测范围包括：认证恢复与失效、路由守卫、统一错误映射、SSE 跨 Chunk 解析、取消、乱序/重复事件、幂等键复用、版本冲突及关键表单校验。
- Playwright 的最终验收必须连接真实本地后端，不得用页面拦截返回固定成功数据替代联调。
- 不得删除失败测试、弱化断言、提交 `.only`/`.skip` 或通过扩大超时掩盖竞态。

## 8. Review 与提交门禁

每次提交前必须完整 Review：

1. 是否只实现当前阶段并严格匹配后端真实契约。
2. 是否存在 Token、密码、个人信息、模型正文或内部错误泄漏。
3. 权限、路由、状态、版本、幂等和 SSE 生命周期是否正确。
4. TypeScript 类型、注释、组件边界和错误状态是否清晰。
5. 测试是否覆盖本次风险并已实际执行。
6. 是否存在无关改动、调试输出、假数据、空按钮、TODO 或生成产物。

Review 未通过、问题未处理、测试未完成或阶段记录未更新时，严禁提交。修复后必须重新 Review 受影响内容并重新执行相关测试。
